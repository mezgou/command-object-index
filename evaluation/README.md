# Оценка алгоритмов

Набор запросов с ожидаемыми ответами и скрипт, который прогоняет через него все алгоритмы из [algo/config.py](../algo/config.py). Новый алгоритм попадает в оценку сам, как только его зарегистрировали.

```bash
python3 -m evaluation.run                                   # все алгоритмы, сводка в консоль
python3 -m evaluation.run -a levenshtein-combinations       # только выбранные
python3 -m evaluation.run --show-misses 20                  # плюс запросы, где нужной команды нет в топ-3
python3 -m evaluation.run --report evaluation/report.md     # отчёт в Markdown (таблицы для слайдов)
python3 -m evaluation.run --latency-scale 1,5,10            # задержка на каталоге, увеличенном в 5 и 10 раз
python3 -m evaluation.run --catalog data/commands.json      # каталог из интерфейса вместо catalog.py
```

Запускать из корня репозитория; сторонние библиотеки не нужны.

## Набор запросов

[queries.jsonl](queries.jsonl) — одна строка на запрос:

```json
{"query": "алиса включи пожалуйста свет на кухне", "expected": ["включи свет на кухне", "зажги свет на кухне"], "type": "noise"}
{"query": "выключи свет", "expected": [["выключи свет на кухне"], ["выключи свет в спальне"]], "type": "ambiguous"}
{"query": "какая погода завтра", "expected": [], "type": "ood"}
```

Команды указываются каноническим `text` из каталога, а не `index`: индексы сдвигаются при любой правке каталога. `expected` бывает трёх видов:

- **список строк** — правильный ответ один, подходит любая из перечисленных равнозначных команд («включи» и «зажги» свет);
- **список списков** — запрос неоднозначный, каждый вложенный список — одно толкование; правильно переспросить;
- **пустой список** — команды в каталоге нет, правильно отказать.

Необязательное поле `forbidden` перечисляет команды, которые для этого запроса особенно недопустимы: выполнить их — критическая ошибка. Пример — запросы с отрицанием:

```json
{"query": "не включай свет на кухне", "expected": [], "type": "negation", "forbidden": ["включи свет на кухне", "зажги свет на кухне"]}
```

| type | Что проверяет | Пример |
|---|---|---|
| `exact` | точная форма из каталога | включи подсветку в спальне |
| `reorder` | другой порядок слов | свет на кухне выключи |
| `partial` | неполное название | закрой жалюзи |
| `synonym` | слова, которых нет в каталоге | погаси свет на кухне |
| `typo` | опечатки (сгенерированы с фиксированным seed, поле `source` — исходная фраза) | выключп музыку |
| `layout` | набрано в английской раскладке | cltkfq nbit |
| `noise` | лишние слова и параметры | поставь будильник на семь утра |
| `ambiguous` | несколько толкований | дверь |
| `danger` | похоже на опасную команду, но это не она | открой шторы |
| `negation` | просьба чего-то не делать; правильно отказать | не открывай дверь |
| `ood` | не про устройства | расскажи анекдот |

Скрипт и тест `backend/tests/test_evaluation.py` проверяют, что все команды из набора есть в каталоге. Если переименовали команду в каталоге — поправьте её и в наборе.

## Правила

[rules.py](rules.py) задаёт, какие ошибки считать критическими:

- `DANGEROUS` — команды, которые нельзя выполнять по ошибке («открой дверь»);
- `OPPOSITES` — пары с противоположным действием (включи ↔ выключи, открой ↔ закрой);
- `EQUIVALENT` — разные блоки с одинаковым действием, между ними не нужно переспрашивать.

## Метрики

**Ранжирование** — считается по запросам с одним правильным ответом, без всяких порогов:

- **Hit@1** — нужная команда на первом месте; **Hit@3** — в первой тройке (главная метрика для слоя кандидатов: попадёт ли нужная команда в модель после нас); **MRR** — среднее 1/позиция.
- **Варианты@5** — для неоднозначных запросов: какая доля толкований есть в первой пятёрке, то есть сможет ли система переспросить с правильными вариантами.

**Решения.** Контракт `search` не умеет отказывать, поэтому решение принимает скрипт: первая команда выполняется молча, только если её score не ниже **порога** и она обгоняет первую команду с другим действием хотя бы на **зазор**. Иначе — отказ или уточнение. Каждый запрос получает исход:

| Исход | Когда |
|---|---|
| верно | выполнена правильная команда или правильно отказано на неоднозначном / постороннем запросе |
| лишний отказ | правильный ответ был, но система отказалась |
| ошибка | молча выполнена неправильная команда |
| критическая | молча выполнена опасная команда или противоположное действие |

Для ориентира: алгоритм, который всегда отказывает, набирает 22% верных решений — это доля неоднозначных, посторонних и запрещающих запросов в наборе.

Порог и зазор подбираются перебором для каждого алгоритма. В сводке два режима: **лучший** (больше всего верных решений) и **без критических ошибок** (лучший из тех, где их ноль). Порог подбирается на том же наборе, поэтому цифры немного оптимистичны; зафиксировать его можно через `--threshold` и `--margin`.

**Скорость** — p50 и p95 времени одного вызова `search`. `--latency-scale` повторяет замер на каталоге, раздутом копиями команд, и показывает, как растёт время и число форм.

## Сравнение прогонов

Чтобы правка каталога или алгоритма ничего не сломала:

```bash
python3 -m evaluation.run --save evaluation/runs/before.json
# ...правки...
python3 -m evaluation.run --compare evaluation/runs/before.json
```

Скрипт покажет, какие запросы починились, какие сломались и где сменился первый кандидат.

## Как пополнять набор

Добавляйте строки в `queries.jsonl` руками — это и есть разметка. Хорошие кандидаты: новые устройства из каталога в нескольких формулировках, реальные запросы из демо, на которых что-то сломалось, и посторонние запросы, похожие на команды («позвони маме», «включи телевизор», когда телевизора нет в каталоге).
