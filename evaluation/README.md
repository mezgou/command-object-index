# Оценка алгоритмов

[dataset.json](dataset.json) — запросы и ожидаемый результат. [evaluate.py](evaluate.py) прогоняет через них алгоритмы из `algo/config.py` и считает оценку. Перед запуском установите зависимости: `python3 -m pip install -r backend/requirements.txt`.

```bash
python3 evaluation/evaluate.py
python3 evaluation/evaluate.py --algorithms structured tfidf-char --details
python3 evaluation/evaluate.py --threshold 0.9 --json evaluation/report.json
```

`--catalog` позволяет проверить алгоритмы на каталоге, отредактированном в интерфейсе: скопируйте `/data/commands.json` из контейнера (`docker compose cp backend:/data/commands.json commands.json`) и передайте путь.

## Формат датасета

Запись ссылается на блоки по их `text`, а не по номеру: номера меняются при удалении блока.

```json
{"query": "включи свет на кухне и выключи телевизор в спальне", "kind": "несколько команд",
 "expect": ["включи свет на кухне", "выключи телевизор в спальне"]}
{"query": "ыключи свет на кухне", "kind": "неоднозначно",
 "alternatives": ["включи свет на кухне", "выключи свет на кухне"]}
{"query": "не включай свет", "kind": "отказ", "note": "отрицание"}
```

- `expect` — команды, которые нужно выбрать **уверенно**; несколько элементов — несколько команд в одном запросе.
- `alternatives` — уверенного ответа быть не должно, но эти блоки полезно показать среди кандидатов.
- Ни `expect`, ни `alternatives` — правильный ответ — отказ.
- `kind` — тип запроса для разбивки результата, `note` — пояснение для человека.

Скрипт сам проверяет, что все упомянутые блоки есть в каталоге.

## Что считается

**Уверенный ответ** — `decision = accept`, если алгоритм возвращает это поле; иначе — top-1 `score ≥ --threshold` (по умолчанию 0.8, как зелёная рамка в первом MVP). **Ответ алгоритма** — лучший блок каждой `command` или просто top-1.

| метрика | как считается | зачем |
|---|---|---|
| **ИТОГ** | среднее баллов по запросам (ниже) | одно число для сравнения |
| top-1, MRR | место ожидаемого блока среди запросов с одной командой | качество ранжирования |
| полнота@5 | доля ожидаемых блоков в первых пяти | годится ли список как кандидаты для следующего шага |
| верно увер. | доля запросов с `expect`, где алгоритм уверенно выбрал ровно их | польза без переспроса |
| безоп. отказ | доля запросов без `expect`, где уверенного ответа нет | умение не угадывать |
| опасных | число уверенных ответов, которые неверны или не должны были быть уверенными | главный риск: молча выполнить не то |
| p50, p95 мс | время одного вызова `search` после подготовки каталога и проверки результата | задержка |

Балл запроса:

| запрос | алгоритм уверен и прав | алгоритм не уверен | алгоритм уверен, но не прав |
|---|---|---|---|
| с `expect` | 1 | 0.5 × доля ожидаемых в top-5 | 0 |
| без `expect` | — | 0.5 + 0.5 × доля `alternatives` в top-5 | 0 |

Так переспрос всегда лучше ошибки, а полезный список кандидатов лучше пустого.

## Текущая оценка

Выдача TF-IDF теперь ограничена 10 блоками с оценкой не ниже 0.5, поэтому приведённые ниже исторические результаты измерены до изменения фильтра выдачи.

Сравнение коммита коллеги `bc3e6c8` с объединённой версией: 138 одинаковых запросов (137 из коммита и контрольный «зажги кондиционер»), по 42 блока, порог 0.8. На той же машине измерен один прогон каждого варианта; каталоги подготовлены пустым запросом, каждый запрос измеряется при первом предъявлении, а ранее встреченные слова остаются в кэше. Каталог и действия изменились одновременно с нормализацией, поэтому цифры не изолируют вклад одной лемматизации.

Проверить гипотезы о размере символьных n-грамм, бинарном TF, IDF по блокам и неизвестных n-граммах можно через `python3 evaluation/tfidf_experiments.py`. Это исследовательские варианты, а не изменения алгоритма платформы; все используют одинаковое ограничение выдачи, заранее подготовленный индекс и прогретую нормализацию. Результаты получены на том же небольшом датасете, поэтому для выбора параметров нужна независимая проверка.

| Алгоритм | Итог до → после | Top-1 до → после | Опасных до → после | p50 мс до → после |
|---|---|---|---|---|
| Левенштейн | 0.789 → 0.816 | 0.898 → 0.875 | 6 → 5 | 45.623 → 20.107 |
| TF-IDF | 0.769 → 0.790 | 0.989 → 1.000 | 24 → 22 | 0.403 → 0.256 |
| structured | 0.989 → 1.000 | 1.000 → 1.000 | 1 → 0 | 0.156 → 0.138 |

Структурный алгоритм после объединения сохраняет явные антонимы, а разрешённые синонимы берёт из каждого блока. В новом контрольном запросе исходная версия уверенно выбирала кондиционер, объединённая — просит уточнение. Прогон проведён до удаления дублирующего идентификатора `structured-morph`; он работал идентично `structured`. Ограниченный синтетический датасет не доказывает безопасность на реальных запросах. Полные отчёты: [до](before-integration.json), [после](after-integration.json).

Для текущего каталога и датасета повторите `python3 evaluation/evaluate.py --details`. Сохранить отчёт по всем запросам можно так:

```bash
python3 evaluation/evaluate.py --json evaluation/report.json
```

Результаты зависят от версии каталога, датасета и машины. Старые числа ниже относятся к версиям до объединения изменений и не представляют результаты текущей версии.

## Историческое сравнение схемы и нормализации

До: коммит `4fa917c`, исходный каталог на 44 блока и [исходный набор](dataset-before-lemmatization.json). После: прежний локальный каталог на 42 блока и соответствующий набор с теми же 132 запросами, до добавления изменений из ветки коллеги; порог 0.8. В обоих случаях использовался один и тот же компьютер и Python 3.14 с pymorphy3. Тайминги — один последовательный прогон: заранее подготавливаются морфология и каталог пустым запросом, каждый запрос датасета измеряется при первом предъявлении, результаты валидируются. Кэш слов и результатов нормализации сохраняется между запросами; холодная инициализация не учитывается.

Ожидаемая метка «зажги свет в спальне» теперь указывает на объединённый блок «включи свет в спальне». Для «зажги свет в гостиной» изменилось и ожидаемое поведение: раньше в каталоге такого действия не было и требовалось уточнение, теперь это синоним и ожидается уверенный выбор. Поэтому сравнение метрик полезно, но не полностью изолирует влияние лемматизации от изменения каталога и одной разметки.

| алгоритм | итог до → после | top-1 до → после | опасных до → после | p50 мс до → после | p95 мс до → после |
|---|---|---|---|---|---|
| levenshtein-combinations | 0.806 → 0.815 | 0.904 → 0.869 | 5 → 4 | 48.261 → 18.459 | 87.889 → 34.568 |
| tfidf-char | 0.777 → 0.796 | 1.000 → 0.988 | 22 → 20 | 0.390 → 0.246 | 0.621 → 0.339 |
| structured | 0.985 → 1.000 | 0.976 → 1.000 | 0 → 0 | 0.149 → 0.135 | 0.308 → 0.310 |
| structured-morph | 1.000 → 1.000 | 1.000 → 1.000 | 0 → 0 | 0.160 → 0.131 | 0.474 → 0.262 |

На запросах типа «словоформа» итог `structured` вырос с 0.857 до 1.000, TF-IDF — с 0.964 до 1.000; у Левенштейна уже было 1.000. На опечатках итог TF-IDF снизился с 0.964 до 0.857: например, «включи музку» остаётся первым кандидатом, но оценка опускается ниже порога уверенности. В том эксперименте `structured-morph` ещё был отдельной записью; сейчас оставлен только `structured` с морфологией.

Первый запрос в новом процессе измерен отдельно на «включи свет на кухне»; медиана трёх запусков, включая построение индексов и инициализацию морфологии, но после импорта модуля: Левенштейн 49.49 → 47.78 мс, TF-IDF 10.83 → 33.90 мс, `structured` 3.16 → 36.20 мс, `structured-morph` 30.05 → 35.72 мс. Инициализация теперь входит в первый вызов всех методов; следующие запросы используют кэши.

Левенштейн нормализует запрос один раз, а формы каталога подготавливает и кэширует до сравнения. Полные ответы на 132 запроса совпали с версией непосредственно до этого рефакторинга; существенного ускорения от удаления повторных вызовов на этом наборе не наблюдалось.

Полные результаты исторического эксперимента по запросам и типам: [до](before-lemmatization.json), [после](after-lemmatization.json). Для воспроизведения исходного состояния используйте коммит `4fa917c`. [Инфографика](../docs/lemmatization-comparison.svg) теперь показывает сравнение объединённой версии с `bc3e6c8` выше.

В объединённой версии синонимы задаются в блоке для конкретного объекта. Явные группы антонимов (`OPPOSITE`) помогают структурному алгоритму выявлять неоднозначные опечатки вроде «выключть».

## Метаморфные тесты

[metamorphic.py](metamorphic.py) берёт каждую фразу датасета, меняет её так, что правильное поведение известно без разметки, и считает нарушения:

| отношение | что меняется | ожидание |
|---|---|---|
| перестановка каталога | блоки в другом порядке (3 перестановки, seed) | то же решение, уверенность и выбранные блоки |
| вежливость и обращение | «пожалуйста …», «… пожалуйста», «привет …» | то же решение, уверенность и те же блоки |
| добавлено «не» | «не …» | никогда не `accept` |
| опечатка-антоним | все однобуквенные опечатки слова, которые в пределах допуска и к нему, и к его антониму («включи» → «вкылючи») | никогда не `accept` |

Запросы с самоисправлением в последние два отношения не входят: изменение в отброшенной части правильно не мешает ответу. Настоящие слова («выключит», «включать») опечатками не считаются, если установлен pymorphy3.

```bash
python3 evaluation/metamorphic.py --details
```

Исторический результат ветки коллеги до объединения (5 622 проверки с установленным pymorphy3; без него опечаток-антонимов на 35 больше), число нарушений / проверок. Он получен по прежней проверке уверенности и выбранных блоков:

| алгоритм | перестановка каталога | вежливость и обращение | добавлено «не» | опечатка-антоним |
|---|---|---|---|---|
| levenshtein-combinations | 0 / 411 | 361 / 411 | 33 / 135 | 2124 / 4665 |
| tfidf-char | 0 / 411 | 155 / 411 | 95 / 135 | 2944 / 4665 |
| structured | 0 / 411 | 0 / 411 | 0 / 135 | 0 / 4665 |
| structured-morph | 0 / 411 | 0 / 411 | 0 / 135 | 0 / 4665 |

В том прогоне фразовые методы допускали нарушения: «пожалуйста» сдвигало уверенность, «не включай» могло оставаться уверенным «включи», а опечатка между антонимами — выбираться уверенно.

В объединённой версии, включая проверку конкретного `decision`, структурный метод прошёл 5 629 проверок без нарушений: перестановка каталога 0/414, вежливость и обращение 0/414, отрицание 0/136, опечатки-антонимы 0/4665.

Тест `MetamorphicTests` в `backend/tests` требует 0 нарушений для `structured`. Отношения уже нашли то, что пропускал ручной датасет: при ничьей первый кандидат зависел от порядка блоков в каталоге; «привет включи» читалось как незнакомый объект «привет»; подсказки менялись от обращения.

Проверки перестановки и вежливости сравнивают решение (`accept`, `clarify`, `reject`, если метод его возвращает), уверенность и выбранные блоки. Ноль нарушений не гарантирует правильности на всех реальных фразах: производные запросы строятся из имеющегося набора и ограниченного списка групп действий.

Важно: датасет составлен автором `structured` одновременно с алгоритмом, поэтому его результат завышен. Добавляйте свои запросы — особенно те, на которых алгоритм ошибается — до того, как подстраивать под них код. Задержка зависит от компьютера.
